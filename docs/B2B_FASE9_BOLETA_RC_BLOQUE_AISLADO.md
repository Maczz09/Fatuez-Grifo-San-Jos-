# B2B-09: paquete 03 y pertenencia al RC

`verifyBoletaPackage` es un bloque candidato aislado: recibe una versión exacta propietaria y lectores privados, verifica el XML individual firmado y distingue el ZIP individual del ZIP del RC. En el segundo caso comprueba un único miembro con snapshot idéntico, reconstruye el RC esperado, verifica su firma y coteja el XML firmado con el ZIP. Relee el registro y los artefactos; una relectura no sustituye una transacción o cerco de concurrencia propietario. No consulta CDR y no produce ni presupone aceptación, envío o no-entrega.

Para conectarlo, la fuente propietaria debe resolver por handle la versión exacta y conservar separadamente XML individual, manifiesto de transporte y, para RC, snapshot del lote, firma, XML y ZIP de ese mismo lote. Debe garantizar procedencia, historia inmutable, aislamiento por emisor, integridad y un protocolo de publicación y lectura consistente. Estas propiedades no las aporta el presente bloque. El llamador debe seguir verificando binding, catálogo, aceptación y fences con las guardas existentes. En la rama exclusivamente 03, sustituir la comparación actual entre ZIP y XML individual por este verificador, ligando sus hashes y versión exacta al registro que se comprueba y a la captura; mantener las relecturas y el cerco completos. Los tipos 01, 07 y 08 deben seguir por su ruta actual. No aceptar datos del cliente ni usar `latest` como fuente.

La aceptación por resumen requiere además el verificador existente de aceptación y su CDR firmado, estado y fence; pertenecer a un RC firmado no prueba aceptación SUNAT. Antes de integrar, adaptar el contrato y el almacenamiento histórico, revisar atomicidad entre documento, lote, catálogo y aceptación, y ensayar el circuito completo con datos sintéticos. La fuente propietaria aún no está acreditada; no se ha conectado el bloque al runtime ni se ha cerrado B2B-09.
