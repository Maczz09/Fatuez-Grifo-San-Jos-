# B2B-09 — almacén histórico PostgreSQL candidato

Candidato aislado para `HistoricalOriginalStore`: no está conectado al runtime, no instala ni aplica migraciones y no autoriza uso real. La escritura valida el contrato completo y utiliza parámetros SQL; cada handle y cada par documento/versión son únicos. Un reintento solo es idempotente si coinciden ambas claves y el JSON completo. Cualquier otro conflicto se rechaza. La lectura es exclusivamente por handle exacto y vuelve a validar tanto el contenido como las columnas indexadas. El esquema candidato rechaza UPDATE, DELETE y TRUNCATE mediante trigger y no sustituye la revisión de permisos ni protege frente a propietarios o administradores capaces de alterar el esquema.

La implementación supone consultas independientes con aislamiento READ COMMITTED: tras `INSERT ... ON CONFLICT DO NOTHING`, una segunda consulta observa al ganador confirmado. No se garantiza ese comportamiento al inyectar un cliente dentro de una transacción de snapshot anterior (REPEATABLE READ o SERIALIZABLE); los errores de transacción se propagan para que el propietario decida si reintenta. La fuente y el control de acceso del pool son responsabilidad del integrador.

`documentZip` representa siempre el ZIP individual del XML, también para 03. No almacena ni sustituye el ZIP o la evidencia del RC, ni demuestra pertenencia a un resumen o aceptación SUNAT. El registro guarda referencias, no bytes; el almacén no verifica existencia ni inmutabilidad de artefactos, firma, procedencia, publicación atómica, aceptación, catálogo de créditos o aislamiento de autorización por emisor. Esas garantías y su recuperación requieren diseño y revisión adicionales antes de integración. B2B-09 y el circuito completo del bloque 1 siguen abiertos.

Prueba explícita: `node tests/historical-original-postgres.e2e.cjs --isolated-synthetic-only`. Usa el helper existente para crear un contenedor PostgreSQL nuevo, imagen local, sin red, sin puertos ni volúmenes persistentes, y lo elimina al finalizar. Solo aplica el SQL candidato en esa base temporal y usa datos ficticios. Comprueba 01/03, lectura exacta, reintentos concurrentes, conflictos por ambas claves, carreras, rechazos de mutación y validación tras la lectura. Las pruebas del contrato, verificador y separación del paquete 03 se ejecutaron además por separado.
